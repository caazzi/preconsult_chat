bloco 1 • desafio de privacidade

o dilema dos dados de saúde & LGPD

o peso da regulamentação (LGPD / HIPAA)

dados de saúde são dados pessoais sensíveis (art. 5º LGPD). Guardá-los atrai enormes riscos:

risco de vazamento

um banco de dados de saúde vazado causa danos morais e materiais irreversíveis aos usuários.

responsabilidade civil & multas

sanções pesadas da ANPD (até R$ 50 mi por infração) e judicialização individual.

custo brutal de compliance

necessidade de direito ao esquecimento, logs de auditoria, criptografia em repouso e suporte 24/7.

onde a maioria dos projetos trava

criadores e startups desistem de serviços de saúde por receio da infraestrutura de banco de dados e custódia de prontuários.

pergunta provocativa:

é possível criar um assistente inteligente de anamnese sem guardar NENHUM dado de saúde do usuário em disco?

solução tradicional: banco de dados & contas alto risco
bloco 1 • a tese do projeto

a tese: "zero-persistence" por design

"a melhor forma de proteger dados médicos em uma aplicação de saúde é NUNCA salvá-los em disco."

arquitetamos o sistema desde o primeiro dia para operar como um pipeline efêmero de transformação de memória.

zero database

sem PostgreSQL, MySQL, SQLite ou MongoDB. nenhuma tabela médica existe no servidor.

zero logins

sem contas de usuário, senhas, tokens persistentes ou armazenamento de perfis.

como funciona na prática?
1. memória temporária (Redis TTL)

estado mantido por no máximo 30 minutos em RAM enquanto o usuário preenche a anamnese.

2. relatório gerado em RAM

o PDF é montado na memória RAM do servidor (`io.BytesIO`) e transmitido como stream.

3. auto-destruição automática

ao baixar o PDF ou fechar a aba, a sessão é completamente descartada sem deixar rastros.

a decisão de usar 100% Python

objetivo do projeto: "levar o ecossistema Python ao limite máximo — construindo do frontend ao backend sem tocar em JS."
UI reativa em Python

componentes declarativos como rx.vstack(), rx.button() e rx.match().

estado unificado

lógica de sessão, rascunho em localStorage e cookies escrita em Python no state.py.

como o Reflex opera nos bastidores

servidor de eventos

zero context-switch

100% do tempo no mesmo ambiente de execução, ferramentas de lint e checagem de tipos Python.

bloco 4 • backend FastAPI & SSE

backend assíncrono com FastAPI

src/preconsult/api/endpoints.py 
# Endpoint de Inicialização de Sessão com Validação Pydantic
@router.post("/session/init", response_model=SessionInitResponse)
async def init_session(request: SessionInitRequest):
    session_data = {
        "age_bracket": request.age_bracket,
        "sex": request.sex,
        "specialist": request.specialist,
        "chief_complaint": request.chief_complaint,
        "conditions": request.conditions,
        "medications": request.medications,
    }
    session_id = await create_session(session_data)
    return SessionInitResponse(session_id=session_id)
por que FastAPI & SSE?
performance async (ASGI)

I/O não-bloqueante ideal para conexões simultâneas de streaming com a LLM.

SSE vs WebSockets

HTTP/2 unidirecional leve com reconexão automática sem sockets abertos no Cloud Run.

contratos Pydantic v2

validação rigorosa de esquemas JSON de entrada/saída sem código manual.

observabilidade Sentry

captura de erros em tempo real filtrando qualquer dado pessoal ou clínico.

bloco 5 • estado efêmero (Redis)

Redis efêmero & fallback em memória

src/preconsult/services/session_service.py 
# TTL de 30 Minutos (1800s) e Fallback em RAM
SESSION_TTL = 30 * 60  # Auto-destruição em 30 min

async def create_session(data: dict) -> str:
    session_id = str(uuid.uuid4())
    key = f"session:{session_id}"
    
    client = get_redis()
    if client is not None:
        await client.hset(key, mapping=_serialize(data))
        await client.expire(key, SESSION_TTL)  # Expiração forçada no Redis
    else:
        logging.info("Sessão em memória (Redis offline fallback)")
    return session_id
resiliência sem persistência

se a instância do Redis expirar ou estiver indisponível, o sistema ativa transparentemente o MemoryRateLimitStore usando time.monotonic().

TTL rigoroso de 30m

garantia matemática de destruição de dados após 30 minutos de inatividade.

zero escrita em disco

absolutamente nenhum dado gravado em HD/SSD do servidor.

nomes e identidades

# Geração determinística de PDF em RAM (ReportLab + BytesIO)
def generate_pdf_report_in_memory(
    form: dict, qa_pairs: list, lang: str = 'en'
) -> tuple[bytes, str]:
    buffer = io.BytesIO()  # Buffer em memória RAM
    c = canvas.Canvas(buffer, pagesize=letter)
    
    # Renderiza formulário estruturado + respostas íntegras
    draw_labeled_section(labels['chief_complaint'], form.get("chief_complaint"))
    for i, qa in enumerate(qa_pairs):
        draw_labeled_section(f"Q{i+1}", qa.get("question"))
        draw_labeled_section("A", qa.get("answer"))
    
    c.showPage()
    c.save()
    pdf_bytes = buffer.getvalue()
    buffer.close()
    return pdf_bytes, filename  # Stream de bytes direto para o browser
vantagens do PDF determinístico
zero custo de LLM no PDF

não gasta tokens nem adiciona latência chamando IA para resumir o relatório.

zero alucinação

o relato do paciente é impresso verbatim exatamente como digitado.

entrega instantânea

stream de bytes enviado via HTTP com header application/pdf.
